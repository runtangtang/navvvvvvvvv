## 2.2 最小的调用代码

```python
import math, time, threading
import rclpy
from rclpy.node import Node
from rclpy.action import ActionClient
from rclpy.executors import MultiThreadedExecutor
from nav_interfaces.action import NavigateTo


class NavCaller(Node):
    """★ 把"走过去"当成一个动作调用。"""

    def __init__(self):
        super().__init__('nav_caller')
        self.cli = ActionClient(self, NavigateTo, '/nav/navigate_to')

    def go_to(self, start, goal, pos_tol=0.05, yaw_tol=0.087, timeout=120.0):
        """
        start / goal: 【6D 位姿】(x, y, z, roll, pitch, yaw)
        ★ 所有角度单位是【弧度】
        ★ 返回 (success: bool, reason: str, result_msg)

        ⚠️ 我们【现在只用到 x / y / yaw】，z / roll / pitch 会被忽略。
           但★建议还是填真实值（以后会用上时客户端不用改），不知道就填 0。
        """
        if not self.cli.wait_for_server(timeout_sec=15.0):
            return False, 'no_server', None

        g = NavigateTo.Goal()
        (g.s_x, g.s_y, g.s_z,
         g.s_roll, g.s_pitch, g.s_yaw) = start
        (g.g_x, g.g_y, g.g_z,
         g.g_roll, g.g_pitch, g.g_yaw) = goal
        g.pos_tol = pos_tol          # [m]
        g.yaw_tol = yaw_tol          # ★ [弧度]！要 5° 就填 math.radians(5)
        g.timeout = timeout
        g.max_speed = 0.0            # 0 = 不限

        send = self.cli.send_goal_async(g, feedback_callback=self._on_fb)
        while not send.done():       # ★ 别用 spin_until_future_complete（会死锁）
            time.sleep(0.05)
        gh = send.result()
        if gh is None or not gh.accepted:
            return False, 'rejected', None

        res_fut = gh.get_result_async()
        while not res_fut.done():
            time.sleep(0.1)
        r = res_fut.result().result
        return bool(r.success), r.reason, r

    def _on_fb(self, msg):
        fb = msg.feedback
        # fb.stage: idle / planning / navigating / fine_approach / heading_align
        # fb.remaining_dist [m] / fb.remaining_yaw [rad] / fb.current_pose
        self.get_logger().info(
            'stage=%s 还剩 %.2fm' % (fb.stage, fb.remaining_dist))
```

## 2.3 用起来

```python
rclpy.init()
n = NavCaller()
ex = MultiThreadedExecutor()          # ★ 必须多线程
ex.add_node(n)
threading.Thread(target=ex.spin, daemon=True).start()

ok, reason, r = n.go_to(
    # 6D 位姿: (x, y, z, roll, pitch, yaw) —— ★ 角度都是【弧度】
    start=(2.07, -2.25, 0.0, 0.0, 0.0, 2.231),
    goal =(5.00,  2.00, 0.0, 0.0, 0.0, 1.571),
)
print('成功' if ok else '失败', reason)
```

# 三、★★★ `s_*` 怎么用 + 三条硬约束

## `s_*` 的机制（2026-09-27 定，务必看清）

```
【第一个 goal】   s_* ⇒ 我们把它当作【狗此刻真实所在】，
                        用它 + 我们里程计此刻的读数 建立坐标系变换 T
                        （T 建立后【全程不变】）

【后续每个 goal】 s_* ⇒ 不重建 T，只【校验】：
                        比较 s_* 和"我们以为狗在哪"
                          差 ≤ 0.20 m ⇒ 一致，沿用现有 T      ← 正常情况
                          差 > 0.20 m ⇒ ⚠️ 报警 + 重建 T      ← 出事了
```

## ★★ 多段任务：`s_*` 必须【链式】给 —— 第 N 段的起点 = 第 N-1 段的终点

```python
# 段1
goal.s_x, goal.s_y, goal.s_yaw = 0.0, 0.0, 0.0
goal.g_x, goal.g_y, goal.g_yaw = 2.0, 0.0, 0.0

# 段2  ★★ 起点 = 上一段的终点，不是重新填 (0,0,0)！
goal.s_x, goal.s_y, goal.s_yaw = 2.0, 0.0, 0.0
goal.g_x, goal.g_y, goal.g_yaw = 3.0, 0.0, 0.0
```

**为什么**：段2 的 `s_*` 若还填 `(0,0,0)`，我们一比对就会发现
"狗明明在 2 米外，你却说它还在原点" ⇒ 差 2m > 0.20 ⇒ 触发【重对齐 + 报警】。
**那是误报，不是 bug** —— 但日志会很脏，而且重对齐会抹掉累积的偏差。

## ★★ 什么时候对齐 —— **不是我们启动节点时，是你发第一个目标时**

```
⇒ 我们从"摆好狗、启动节点"到"收到你的第一个目标"之间【不能碰狗】
```

---

## 三条硬约束（不满足会出错，而且**我们察觉不到**）

```
① ★★★ 【第一个 goal 的】`s_*` 必须是【实测的】，不是"应该是"
    它就是对齐的输入 —— 我们把它当作狗此刻真实所在。
    狗实际停偏 10cm ⇒ 全程都差 10cm。
    ★ 而且这个我们【事后查不出来】：唯一的校验是"后续 s_* 有没有突然改口"，
      第一下说错了查不出来（它就是基准）。
    ⇒ 请确认：第一个 goal 里的 s_* 是【狗实际在哪】还是【按计划应该在哪】？

② ★★ 狗必须【真的停在】你给的那个起点上，并且停稳
    "大概在那个位置"不行。差多少，全程错多少。

③ ★ 角度一律【弧度】（不是度）
    要 5° 的容差 ⇒ 填 0.087。这个坑我们踩过（把度数当弧度 ⇒ 终点朝向差 23°）。

④ ★ 多段：`s_*` 要【链式】（s₂ = g₁）—— 见上面那节
```

## ★ z / roll / pitch 要不要填？—— **建议填真实值，但现在不生效**

**建议：填【场景图坐标系里的真实值】，不知道就填 0**（别留随手的默认值）。

```
理由：
  ① 向前兼容 —— 万一我们以后要用（3D、或者用 roll/pitch 判断"狗站平了没"），
     你们的客户端【一行都不用改】
  ② 排查时有用 —— 日志里有真实的起点姿态，出问题能看出来
  ③ 接口既然定义了这些字段，就该填有意义的数，
     否则将来我们真开始用时会是一个【静默的行为变化】

⚠️ 但现在【我们完全忽略它们】—— 不要指望它们现在有任何效果。
   哪天开始用了，那是【新行为】，我们会提前通知。
⭐ 一句话："可以填，现在不生效；将来会生效，到时我们通知你们。"
```

具体填什么：

```
s_z        狗在场景图里的高度（图里地面 z=0、狗站地上 ⇒ 填 0 或机身中心高度）
s_roll     狗当前的身体侧倾（站平了就是 0）
s_pitch    狗当前的身体俯仰（站平了就是 0）
g_z        目标点的高度（一般 0）
g_roll     希望的最终侧倾（一般 0）
g_pitch    希望的最终俯仰（一般 0）
```


# 五、输出接口

## feedback（10 Hz，一直发）

```yaml
string  stage           # ★ 会真的切换：
                        #   idle            空闲
                        #   planning        规划中（很短，约 200ms，可能采不到）
                        #   navigating      沿路径走
                        #   fine_approach   末端精调（位置）
                        #   heading_align   末端朝向对准
float32 remaining_dist  # 离目标还差多远 [m]
float32 remaining_yaw   # 朝向还差多少 [弧度]
geometry_msgs/PoseStamped current_pose   # 当前位姿（场景图坐标系）
```

## result（任务结束时一次）

```yaml
bool    success         # ★ 到没到 —— 只看这个就够了
geometry_msgs/PoseStamped final_pose     # 实际到位姿
float32 internal_error  # ⚠️ 见下，【不是】真实误差
float32 uncertainty     # ⚠️ 估计，不是测量
string  reason          # 失败原因，见下
float32 elapsed         # 用时 [s]
```

### reason 的取值 + 建议你们的处理

| reason | 含义 | 你们应该怎么做 |
|---|---|---|
| `arrived` | ✅ 到了 | 继续下一步 |
| `timeout` | 超时 | 可重试 |
| `blocked` | 被人/物挡住 | **等一等可以重试** |
| `stuck` | 卡住了走不动 | 可重试，或者换个目标点 |
| `turn_shift` | 位置走到了，但末端转身把位置挪偏了 | **直接重试一次** |
| `no_path` | 地图上过不去 | ★ **重试没用**，换目标点或换方案 |
| `aborted` | 收到急停（含你们主动 cancel） | 停下来查原因 |
| `source_error` / `stale` / `no_pose` | 里程计出问题 | 检查系统 |
| `planning_failed` | 规划失败 | 检查地图/目标 |
| `internal_error` | 内部异常 | 查日志 |

★ **`blocked` 和 `no_path` 故意分开** —— 前者等等能过，后者重试一万次也没用。

## ⚠️ 关于 `internal_error` —— 请务必理解这一条

```
它是在【我们自己里程计坐标系】里收敛出来的误差，闭环会把它压到 ~0。
⇒ ★ 它【不是】真实世界的误差，是一个恒等式。
⇒ 真实误差 = 我们的误差 + 起点位姿误差 + 场景图误差
              ↑ 我们只能控制这一样

同理 uncertainty 是"我们对自己位置不确定度的估计"（现在很粗：走过距离×2%）。
它的意思是：**别把我们的坐标当真值**。
```

# 六、取消 / 中断

```python
goal_handle.cancel_goal_async()      # ★ 发出去就停，1 秒内安全停下
# 我们会：走 Navigator 的 abort 通道 → 跟随器/精调循环立刻中止 → settle() 安全站定
# result 的 reason 会是 'aborted'
```

**★ 同一个时刻只能跑一个任务。** 任务进行中来新目标会被【拒绝】（goal 被 REJECT）。
想换目标：先 cancel，等 result 回来，再发新的。

# 七、我们能承诺什么 / 不能承诺什么

## 能承诺

```
✅ 位置精度：达到 pos_tol + 滑行量（默认 5cm + 3.1cm ≈ 8cm）
✅ 朝向精度：1~3°
✅ 多段不累积误差（只对齐一次，各段直接接着走）
✅ 任何失败都会安全停下，并给一个明确的 reason
✅ feedback 10Hz，能画进度条
```

## 不能承诺

```
❌ 【绝对精度】—— 见上面 internal_error 那条
❌ 到达时间 —— 被挡住时要等，这个控制不了
❌ 动态障碍 —— 还没做（下一步）
❌ 末端 3cm 级 —— 现在的最小可控位移是 8cm
```

## ★ 一句话

> **"给我们两个位姿，我们把狗精确地送过去，并如实告诉你结果。
> 但我们的'误差'是在我们自己坐标系里的 ——
> 真实精度取决于你们给的起点有多准。"**

---

## ★★ 场景坐标系是怎么定的（★ 别理解错）

**收到【第一个 goal】时**做一次【开机对齐】，机制是：

```
把【我们里程计那一刻的读数】记作 P_odom   （里程计自己的相对坐标系）
把【这次 goal 里的 s_*】     记作 P_start  （场景图坐标系）
建立刚体变换 T，使得      T(P_odom) = P_start
⇒ 之后里程计的所有读数都通过 T 转到【场景系】；T 建立后【全程不变】
```

★★ **不是我们启动节点时做的，是收到你的第一个目标时做的**
⇒ 所以【我们摆好狗、启动节点】到【你发第一个目标】之间**不能碰狗**。

**所以：**

```
你给的 s_* = (1, 1, 0, 0, 0, 0)
  ⇒ 发这个目标的那一刻，狗站的地方 = 场景图里的 (1, 1)，朝向 = 场景系 +x

你给的 s_* = (0, 0, 0, 0, 0, 0)      ← 空图时最常用（原点随意）
  ⇒ 狗站的地方 = 场景系原点，朝向 = +x
  ★ 注意：这时"狗的位置 = 原点"才对；给了别的 s_* 就不是了
```

## ★★★ 唯一的前提（也是全系统最脆弱的一环）

```
★ 狗必须【真的】站在你说的那个位姿上。

   差多少，全程错多少 —— 而且我们【没有任何手段能发现】。
   因为我们只能测【相对位移】，没有外部绝对参考。

⇒ 所以：如果 start 是 (1,1,0)，那就必须把狗【准确地】摆到 (1,1)、朝 +x。
   摆偏 10cm ⇒ 之后每一步都偏 10cm。
```

## ⚠️ 一个容易搞混的点：0.5m 的近目标**查不出起点摆错**

```
你说"狗在 (2.07,-2.25)"，我们就把里程计此刻读数钉在那儿。
⇒ 哪怕狗其实站偏了 10cm，0.5m 的近目标照样走得对（因为起点就是原点）
⇒ 那 10cm 全程都在，而且【任何一级验证都查不出来】

★ 唯一能查的办法：★ 人在现场，眼睛看 ——
    "你认为狗在哪" vs "狗实际在哪"
```

# 九、出问题时的对照表

| 现象 | 可能原因 | 找谁 |
|---|---|---|
| 连不上（等不到服务端） | 不在同一网段 / 节点没起 | 双方一起查 |
| 目标被 REJECT | 已有任务在跑（同一时刻只跑一个） | 先 cancel，等 result 回来再发 |
| 走了但方向不对 | 场景系坐标轴搞反/差 90° | ★ 双方对坐标系定义 |
| 走的距离差很多 | 起点位姿不准 / 尺度 | 先量卷尺再讨论 |
| **我们日志里出现"⚠️ 起点和我们的认识差太多 ⇒ 重新对齐"** | ★ 这一段的 `s_*` 和上一段的 `g_*` 差了 >0.20m ⇒ **多半是 `s_*` 没链式给** | ★ 你们检查 `s_*` 是不是 `s₂ = g₁` |
| result 的 reason=no_pose | 对齐那一步拿不到位姿 | 我们查日志 |
| reason=no_path | 目标点在障碍里，或者障碍挡死 | 查目标点 + 查图 |
| 误差 6~8cm | ★ 这是我们现在的**能力上限**，不是 bug | 见 §七 |

# 十、还需要你们确认的

```
□ ★★★ 【第一个 goal 的】s_* 是【实测】还是【标称】？（决定我们的精度上限）
      ★ 而且是"狗实际停在哪"还是"按计划应该在哪"？
□ 你们给的位姿坐标轴和我们的"x=0°、逆时针为正"一致吗？
□ 目标位姿本身的精度（如果目标点就偏了 20cm，那不是我们的问题）
□ 一次给全部航点，还是分多次调用？
□ 导航在跑的时候，别人能不能抢控制权（遥控器/别的模块）？
```
